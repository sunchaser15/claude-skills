# workflow-contract

Личный скилл владельца для запуска новых проектов. Регламент из `~/.claude/CLAUDE.md` (4 этапа) здесь превращён в конкретные шаги. Переход к следующему этапу только после завершения предыдущего: смысл в том, чтобы код писался под зафиксированные требования и проверялся тестами, а не под первое впечатление от идеи. Язык общения русский.

Скрипты лежат рядом: `~/.claude/skills/workflow-contract/scripts/`. Ниже `$S` = этот путь.

## Этап 1. Интервью

Ничего не создавай: ни папок, ни файлов, ни кода. Только вопросы.

1. Перечитай идею из аргументов. Если владелец уже ответил на часть вопросов в самом запросе, не переспрашивай, а зафиксируй эти ответы. Если он ответил на всё и заранее одобрил спеку, интервью можно пропустить, но всё, что ты додумал сам (таблицы, лимиты, поведение в непокрытых случаях), пойдёт в `SPEC.md` → «Решения агента» и будет показано владельцу в отчёте: заранее одобрено только то, что он сказал сам.
2. Задай один блок вопросов через `AskUserQuestion` (до 4 вопросов за вызов; если нужно больше, второй вызов). Варианты ответа предлагай конкретные, первым ставь рекомендуемый с пометкой «(Рекомендую)». Покрыть:
   - **Суть и пользователь**: что делает, кто пользуется, главный сценарий.
   - **Стек и среда**: язык/фреймворк; где живёт (Мак `~/projects`, сервер Польша/NL, браузер, Telegram); деплой нужен или нет.
   - **Входы и выходы**: форматы данных, команды, API, файлы; пример одного входа и ожидаемого выхода.
   - **Граничные случаи**: пустой ввод, огромный ввод, кириллица, дубли, сеть недоступна, лимиты внешних API.
   - **Ошибки**: что видит пользователь при ошибке, коды выхода/ответов, логи, ретраи.
   - **Секреты и внешние сервисы**: токены ботов, API-ключи (только через `.env`, никогда в код).
   - **Имя**: папка и репо, латиница в kebab-case.
3. Неясное после ответов — ещё один короткий блок, а не догадки. Не задавай вопросов, ответ на которые очевиден из контекста или памяти (например, аккаунт GitHub известен: sunchaser15).

## Этап 2. Спецификация и каркас

1. Проверь, что `~/projects/<имя>` не существует (и что репо `sunchaser15/<имя>` не занят: `gh repo view sunchaser15/<имя>`). Если занято, предложи другое имя.
2. Каркас: `bash $S/scaffold.sh <путь> <стек>`, стек: `python | node | web | swift | other`. Скрипт создаёт папку, `git init -b main`, `.gitignore` под стек (с `.env`, `*.db`, секретами), `README.md`, `CLAUDE.md` (подключает `SPEC.md`) и пустой шаблон `SPEC.md`. Повторно запускать безопасно: существующие файлы не перезаписывает.
3. Заполни `SPEC.md` по шаблону (см. сам файл): цель, вне рамок, стек, входы/выходы, требования с номерами `R1, R2…`, граничные случаи, ошибки, критерии приёмки, план по шагам. В плане раздели код на модули с чёткими интерфейсами и разложи их по волнам: в одной волне модули не зависят друг от друга (их можно делать параллельно), следующая волна опирается на предыдущую. Для каждого модуля укажи его файлы и какие `R*` он закрывает. Каждое требование должно быть проверяемым тестом; если нельзя проверить автоматически, пометь `(ручная проверка)` и объясни почему.
4. Покажи владельцу `SPEC.md` (кратко в чате + ссылка на файл) и получи явное «ок» или правки. После «ок» спецификация — контракт: дальше её не меняешь молча. Если по ходу выяснилось, что пункт невыполним или неверен, остановись, предложи правку, получи согласие, обнови `SPEC.md` с пометкой в разделе «Изменения контракта».
5. Первый коммит и GitHub: `git add -A && git commit -m "spec: контракт проекта"`, затем `bash $S/github_push.sh <путь>`. Скрипт создаёт **приватный** репо, отказывается пушить в не-PRIVATE и останавливается, если в коммитах похоже на секреты. Создание репо владелец разрешил заранее этим скиллом; если скрипт упал, покажи вывод и не обходи проверки руками.

## Этап 3. Тесты до кода

1. Поставь тест-раннер под стек по `references/test-stacks.md` (там команды установки и запуска). Команду прогона тестов запиши в `CLAUDE.md` проекта и в `SPEC.md` → «Как проверить».
2. Напиши тесты на **каждое** требование `R*` и каждый граничный случай. В имени или докстринге теста укажи номер требования (`test_r3_empty_input_returns_error`), чтобы в отчёте было видно покрытие. Тестируй поведение через публичный интерфейс (функции, CLI, HTTP), а не внутренности: тогда реализацию можно менять свободно.
3. Тесты каждого модуля из плана клади в свой файл (`tests/test_<модуль>.py`, `test/<модуль>.test.js`): так модуль можно отдать воркеру вместе с его тестами.
4. Внешние сервисы (Telegram, HTTP API, БД) в тестах подменяй фейками/моками; реальные ключи в тестах не нужны.
5. Создай пустые заглушки модулей (сигнатуры без логики, `raise NotImplementedError` / `throw new Error("not implemented")`), чтобы тесты падали на поведении, а не на импорте. Заглушки и есть контракт интерфейса для воркеров: имена, сигнатуры, типы, докстринги с поведением.
6. Запусти тесты. Убедись, что они **красные** и падают по правильной причине. Ни один тест не должен проходить на заглушках: если проходит (например, исключение заглушки случайно даёт ожидаемый код выхода 1), тест слишком слабый — усиль проверку (текст ошибки в stderr, конкретное значение), пока он не упадёт. Покажи владельцу короткую сводку: сколько тестов, все упали, примеры причин.
7. Коммит `test: красные тесты по SPEC R1–Rn` и `bash $S/github_push.sh <путь>`.

## Этап 4. Реализация и самопроверка

**Кто пишет код.** Если в плане **2 и больше независимых модулей** со своими тестами, работай в режиме оркестратора: ты планируешь, раздаёшь и принимаешь, а модули пишут воркеры на Sonnet — так дешевле и параллельно. Порядок в `references/orchestrator.md`, прочитай его перед стартом. Если модуль один или всё связано в одну цепочку, накладные расходы на раздачу больше выигрыша — пиши сам по пунктам ниже. Склейку модулей (точка входа, CLI, main) и всё, что осталось после воркеров, всегда доделываешь сам.

1. Пиши код только ради зелёных тестов, по шагам плана из `SPEC.md`. После каждого заметного изменения запускай тесты сам.
2. Упал тест — читай лог, чини сам. Не правь тест, чтобы он прошёл, если тест верно отражает контракт; если тест неверен, это изменение контракта (см. этап 2, п. 4).
3. Не пиши «готово/работает» без фактического прогона. Задача выполнена, только когда весь набор зелёный.
4. Если проект запускаемый (CLI, бот, сайт), сделай один реальный прогон вне тестов (для веба — превью в браузере), чтобы увидеть, что всё собирается вместе.
5. Финал:
   - `git commit -m "feat: реализация по SPEC"` и `bash $S/github_push.sh <путь>`.
   - Добавь проект в массив `PROJECTS` файла `~/projects/push-to-github.sh` (формат `папка:репо`).
   - Сохрани в память файл `proj-<имя>.md` (суть, стек, где живёт, как запустить тесты, раздел «GitHub») и строку в `MEMORY.md`.

## Финальный отчёт

```
## <Имя проекта> — готово

**Тесты:** <N> из <N> зелёные (<команда прогона>)
<вывод последнего прогона, сокращённый до итоговых строк>

**Покрытие требований:**
| R | Что | Тесты |
|---|-----|-------|
| R1 | … | test_r1_… |

**Что сделано:** 2–4 строки.
**Ручная проверка:** что запускал вне тестов и что увидел.
**GitHub:** https://github.com/sunchaser15/<имя> (private), последний коммит <sha>.
**Решения агента:** что додумано сверх ответов владельца (из SPEC.md) — на подтверждение.
**Отклонения от контракта:** нет / список с согласием владельца.
**Что осталось:** если есть.
```

## Если что-то пошло не так

- `gh` не залогинен или лимит GitHub на создание репо («too many repositories»): продолжай работу локально с коммитами, скажи владельцу, повтори `github_push.sh` позже.
- Скрипт нашёл похожее на секрет: покажи строку (замаскировав значение), вынеси значение в `.env`, перепиши коммит, если секрет уже в нём (`git reset --soft HEAD~1`), и только потом пушь.
- Проект на сервере, а не на Маке: каркас и тесты всё равно на Маке в `~/projects/<имя>`, деплой отдельным шагом в плане `SPEC.md`.
