# Режим оркестратора (этап 4)

Ты — координатор: план, раздача, приёмка. Модули пишут воркеры (субагенты на Sonnet), каждый в своём `git worktree`, чтобы не перетирать файлы друг друга. Зачем так: дорогая модель тратит токены на решения, а не на рутинный код, а независимые модули делаются параллельно.

`$S` = `~/.claude/skills/workflow-contract/scripts`, `$P` = путь проекта.

## Перед стартом
- Красные тесты закоммичены в `main` (этап 3), рабочее дерево чистое (`git -C $P status --porcelain` пусто). Воркеры ответвляются от `main`, всё незакоммиченное они не увидят.
- По плану из `SPEC.md` выпиши волну: модули без взаимных зависимостей. Для каждого: имя задачи (kebab-case), файлы, которые воркер пишет, файл(ы) его тестов, команда прогона только его тестов.
- Если два модуля пишут в один файл, это не одна волна: либо разнеси по файлам, либо сделай последовательно.

## Волна
1. Для каждого модуля: `bash $S/worktree.sh add $P <задача>` → печатает путь worktree `$W`.
2. Подготовь окружение там, где его нет в git: node — `npm ci` (или `npm install`) в `$W`; python + uv — ничего, `uv run` сам создаст `.venv`. Нужный `.env` для тестов не копируй: тесты работают на фейках.
3. Запусти всех воркеров волны **в одном сообщении**, каждого через Agent с `model: "sonnet"` и `run_in_background: true`. Параметр `isolation` не используй: worktree уже создан скриптом. Промпт — по шаблону ниже.
4. Пока воркеры работают, не трогай их worktree и `main`.

## Приёмка (по каждому воркеру, как только он закончил)
Отчёту воркера не верь на слово — проверь сам:
1. `bash $S/worktree.sh check $P <задача> <пути тестов>` — всё закоммичено, тесты не тронуты. Код 3 (тесты изменены) — работа не принимается: откати изменения тестов и верни задачу воркеру. Код 4 — попроси воркера закоммитить.
2. Прогон тестов модуля в `$W` своей командой. Должен быть полностью зелёный.
3. Беглый взгляд на дифф (`git -C $P diff main...task/<задача> --stat` и сам код): нет ли заглушек вида «вернуть ожидаемое значение для теста», лишних файлов, секретов.
4. Ок → `bash $S/worktree.sh merge $P <задача>`. После **каждого** слияния — полный набор тестов в `$P`: тесты ещё не сделанных модулей остаются красными, но ранее зелёные не должны покраснеть.

## Если не вышло
- **Тесты не зелёные / работа не принята:** прочитай лог, отправь тому же воркеру (SendMessage на его адрес) одну повторную попытку с конкретной подсказкой: какой тест, что не так, где искать. Не помогло — доделай сам в его worktree, закоммить, и приёмка как обычно.
- **Конфликт при слиянии (код 5):** `main` остаётся в состоянии слияния. Разреши сам с учётом обоих модулей, `git commit`, прогони полный набор, затем `git worktree remove <путь> && git branch -d task/<задача>`.
- **Воркер говорит, что тест неверен или контракт невыполним:** это вопрос изменения контракта (этап 2, п. 4) — решаешь ты с владельцем, не воркер.
- Брошенные worktree после сбоя: `git -C $P worktree list`, лишние убери `git worktree remove --force`, ветки `git branch -D task/...`.

## После всех волн
Склейка (точка входа, CLI, wiring) — сам. Полный набор зелёный → обычный финал этапа 4 и отчёт. В отчёте добавь строку: какие модули делали воркеры, сколько повторных попыток, что пришлось доделать самому.

## Шаблон промпта воркера

```
Ты — воркер. Реализуй один модуль проекта так, чтобы его тесты стали зелёными.

Рабочая папка (git worktree, ветка task/<задача>): <$W>
Работай только в ней. Не трогай другие папки и ветку main.

Модуль: <имя> — <одна строка, что делает>
Пиши в файлы: <список>
Тесты модуля (менять НЕЛЬЗЯ, ни одного символа): <пути>
Команда прогона: cd <$W> && <команда только для этих тестов>

Контракт: интерфейс задан заглушкой в <файл> (сигнатуры и докстринги не меняй).
Требования из SPEC.md, которые закрывает модуль:
<выдержка R*/E* дословно>

Правила:
- Цель — зелёные тесты честной реализацией. Не подгоняй код под конкретные значения из тестов.
- Запускай тесты сам после каждого изменения; не пиши «готово» без прогона.
- Не добавляй зависимостей без крайней нужды; если добавил — объясни зачем.
- Если считаешь, что тест противоречит требованию, не обходи его: остановись и опиши проблему в отчёте.
- В конце: git add -A && git commit -m "feat(<задача>): <кратко>" в своей ветке.

Отчёт (коротко): итог прогона тестов (последние строки вывода), список изменённых файлов, что было непросто, вопросы к контракту если есть.
```
